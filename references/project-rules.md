# 全工程框架基本规则

## 适用范围

本文件规定所有基于本 Skill 新建、生成或改造的 STM32 + HAL + FreeRTOS 工程必须共同遵守的基础约束。通信增强层、硬件驱动层、应用层以及系统装配代码都不得绕过这些规则；模块专用规范与本文件冲突时，以本文件为上位约束，并向用户说明冲突。

## 头文件规范

头文件是模块开发者与模块使用者之间的接口边界。它的目的不是公开实现细节，而是同时做到：开发者可以保护和调整模块内部数据，使用者只依赖稳定、充分且独立的公开接口即可完成初始化、配置、控制、状态读取和事件绑定，无需阅读源文件或直接操作内部状态。

参考 `YS_Moto.h` 的组织方式，头文件应遵守以下规则：

1. 内容按“功能包概述、必要的 `include`、公开配置宏、公开类型与结构体、回调类型、公开接口函数”组织，并使用头文件保护宏。
2. 功能包概述应说明模块主要功能、所属系统层级、硬件连接、CubeMX 等非代码配置、运行上下文和关键注意事项，使使用者只阅读头文件就能正确完成集成。
3. 头文件只包含其公开声明自身所必需的依赖。仅由源文件内部使用的头文件、变量、辅助类型和函数声明必须留在 `.c` 文件中，避免把内部依赖传播给所有使用者。
4. 每个独立硬件或功能实例使用一个公开对象结构体集中表达。公开结构体只保留使用者确实需要的内容：
   - 可观察状态，例如当前位置、当前速度和错误状态；这些字段对使用者是只读契约，涉及物理量时必须标注单位；
   - 允许使用者修改的配置，例如 PID 参数、目标值或工作选项，并明确合法范围和修改时机；
   - 必要的硬件资源标识，例如设备地址或 HAL 句柄，但使用者不得绕过模块接口直接改变其运行状态；
   - 应用组合所需的 `fatherArgs`、事件回调函数指针及对应的绑定、解绑接口。
5. 开发者内部状态采用不透明私有结构体保护。头文件只做前置声明，并在公开对象中保存私有指针；私有结构体的完整定义、内部状态、缓存、计时量和控制过程只能出现在 `.c` 文件中：

```c
typedef struct _Hardware_Private Hardware_Private;
typedef struct _Hardware Hardware;

typedef void (*Hardware_Callback)(Hardware *self, void *fatherArgs);

struct _Hardware {
    /* 使用者可读取的状态，以及明确允许修改的配置 */
    float nowPosition;
    float nowVelocity;

    /* 开发者私有数据入口；使用者不得解引用或修改 */
    Hardware_Private *priVari;

    /* 应用层组合与事件出口 */
    void *fatherArgs;
    Hardware_Callback refreshDataCallback;
};
```

6. 公开接口必须足够完整、彼此独立。使用者应能通过头文件声明的函数完成对象初始化、控制命令、状态获取、参数设置、回调绑定与解绑、停止和错误处理，不得要求使用者访问私有结构体、源文件静态变量或依赖某个未公开的调用副作用。
7. 不应为了隐藏必要能力而过度私有化。如果使用者确实需要某项操作，应增加语义明确的公开函数；不要迫使使用者通过修改公开结构体内部字段、复制模块内部代码或直接调用底层 HAL 来实现。
8. C 语言无法阻止使用者改写公开字段，因此“只读状态”既是接口契约，也是审查要求。需要强制保护的状态不得直接公开可写字段，应改为私有保存并提供只读查询函数。


## 1. 默认启用串口1作为系统日志通道

- 除非目标 MCU 没有 USART1、引脚存在不可调和的硬件冲突，或用户明确指定其他日志通道，否则必须启用串口1资源。
- 串口1默认承担系统级日志、启动信息、错误诊断、运行状态和调试信息到上位机的输出，不应被某个器件驱动独占。
- CubeMX 资源规划必须为串口1保留所需的时钟、GPIO、NVIC，以及项目发送方案需要的 DMA 资源；波特率、数据位、停止位和校验方式作为项目配置明确记录。
- FreeRTOS 启动后，系统日志应通过通信增强层的 UART1 实例发送，统一处理资源占用和异步排队；业务模块不得绕过通信增强层直接争用 `huart1`。
- ISR 和 HAL 回调中不得直接格式化或阻塞发送日志。中断中只记录必要状态或通知日志任务，由任务上下文完成输出。
- 如果不能启用串口1，必须在设计说明中记录原因，并明确替代日志通道、对应硬件资源和上位机连接方式。不得在没有说明的情况下生成一个完全缺少系统日志出口的工程。

## 2. 全局规避占用 CPU 的阻塞式延时

- 通信增强层、硬件驱动层、应用层和 FreeRTOS 任务中禁止使用 `HAL_Delay()` 实现控制等待、周期调度、通信重试、器件稳定等待或状态切换。
- 任务上下文需要等待时，使用 `osDelay()` 让当前任务进入阻塞态并释放 CPU，使其他任务继续运行。这是任务级非占用等待，不代表调用当前任务会立即返回。
- 周期任务优先采用基于绝对唤醒时刻的周期延时机制，例如 CMSIS-RTOS2 可用接口存在时使用 `osDelayUntil()`，避免任务执行时间累积造成周期漂移。
- `osDelay()` 和 `osDelayUntil()` 只能在 RTOS 任务上下文中调用。ISR、HAL 中断回调以及调度器启动前不得调用；中断中应通过任务通知、队列、信号量或事件标志唤醒任务继续处理。
- 调用任务延时前必须退出临界区，并且不得持有会阻塞其他任务推进所必需的互斥量或通信资源锁。
- `osDelay(1)` 表示一个内核 tick，不应直接假定为 1 ms。涉及毫秒参数、超时和任务周期时，必须依据 FreeRTOS tick 频率换算或使用系统 tick 判断经过时间。
- 调度器启动前如确有芯片上电、时钟稳定或器件手册强制要求的等待，优先使用硬件状态标志、定时器或带截止条件的轮询。只有无法替代时才允许局部、有限且有依据的启动阶段等待，并记录原因；不得把这种例外扩展到 RTOS 运行阶段。

## 3. 全工程尽可能规避优先级配置

### 设计原因

1. **避免形成不可移植的隐含时序依赖。** 基于优先级调通的工程，可能只在当前任务集合、模块组合和负载条件下正常运行。更换一个驱动模块、增加一个任务或改变应用方式后，原来的默认优先级关系可能造成执行顺序改变、任务饥饿、数据处理延迟或偶发竞态，从而产生难以预料和复现的缺陷。模块的正确性不应依赖某个具体工程恰好采用的优先级排列。
2. **降低模块之间的耦合，保护代码封装性。** 优先级表达的是多个任务或中断之间的相对关系，天然属于系统级组合属性。如果一个独立模块必须知道自己应高于或低于其他模块才能工作，它就把外部模块关系带进了自身实现，说明接口、状态同步或资源仲裁没有完全封装。模块应通过明确的输入输出、状态机、队列、事件和资源所有权独立运行，而不是通过优先级暗中影响其他模块。
3. **优先级不能统一控制任务与中断中的执行。** STM32 上的 FreeRTOS 是单核分时运行系统，RTOS tick 定时器中断负责推进系统时基、解除任务延时，并在需要时触发任务切换；普通任务代码实际运行在线程上下文，并不是运行在 tick 中断内部。任务优先级只决定多个就绪任务之间的调度，外设 HAL 回调等中断内程序则由另一套 NVIC 中断优先级决定。因此，任务优先级不能保证中断回调内部的执行顺序，随意叠加 NVIC 优先级还可能破坏 FreeRTOS 的可调用中断范围。若大量业务代码放在中断中，优先级配置更难达到预期效果；正确做法是缩短 ISR，并把后续处理转移到具有明确接口的任务中。

基于以上原因，优先级只用于满足经过证明的实时边界和硬件约束，不能作为保证一般功能正确性的主要机制。

- 不依赖任务优先级、中断抢占优先级、消息优先级或发送插队来维持正常业务顺序。模块协作优先使用明确的状态机、队列、事件、通知和固定数据流。
- FreeRTOS 任务在满足调度要求的前提下，尽可能采用统一的默认优先级和最少的优先级层级；不得仅因为某个功能“更重要”就随意提高任务优先级。
- 不使用动态调整任务优先级作为一般控制手段，避免产生难以复现的抢占关系、优先级反转和任务饥饿。
- 通信发送默认使用 FIFO，不设置高优先级插队。确有紧急数据需求时，优先采用独立通道、独立队列或明确的安全事件路径，而不是修改普通数据的队列顺序。
- NVIC 中断优先级只配置满足 HAL、FreeRTOS 可调用中断范围和硬件实时性的必要差异，不进行无依据的精细分级。
- 只有硬实时控制、安全保护或芯片中断约束能够证明需要时，才允许引入差异化优先级。必须记录优先级数值、设置依据、抢占关系、允许调用的 RTOS API，以及对其他任务和中断的影响。

## 4. 保持执行上下文边界

- ISR 和 HAL 回调只完成必要的数据搬运、状态记录、时间戳采集及任务唤醒，不执行延时、动态格式化、复杂协议解析、应用状态机或长循环。
- 可能等待资源、分配较大内存或执行复杂运算的逻辑必须转移到任务上下文。
- 每个公开接口应明确允许的调用上下文；任务专用接口不得从 ISR 间接调用。

## 5. 默认使用 HAL 公共接口

- 平台层由 STM32CubeMX 生成 CMSIS、HAL、时钟、GPIO、DMA、中断和外设初始化代码。
- 通信增强层与硬件驱动层默认只调用 HAL 公共 API，不主动引入 LL 库，也不直接操作外设寄存器。
- 只有用户明确要求且 HAL 无法满足已声明需求时，才单独评估 LL 或寄存器级实现，并记录必要性、影响范围和移植风险。

## 6. 遵守分层和资源所有权

- 应用层不得直接调用 HAL 或访问外设寄存器；硬件驱动层不得包含机器人工作模式和任务编排；通信增强层不得解释机器人业务命令。
- 外设句柄、DMA 通道、发送缓冲、接收缓冲和回调注册表必须有唯一且明确的管理模块，不得由多个层级无协调地修改。
- 跨任务、回调或 DMA 使用的数据必须明确所有权、有效期、容量和完成后的释放责任。

## 7. 多硬件实例使用编译期固定结构体数组

- 在平台层、通信增强层、硬件驱动层等任一硬件相关层级中，如果同一段代码需要为多个同类型硬件实例执行接收、解析、状态更新、控制或其他数据处理，必须由该层生成一个保存全部实例的固定大小结构体数组。
- 数组大小必须由编译期宏定义参数决定。该宏表示当前项目实际连接或配置的同类型硬件数量，必须依据原理图、BOM、设备 ID 分配或用户提供的硬件配置确定，并随实际硬件增减而修改。
- 禁止把该数组实现为可变长度数组（VLA）、按运行时参数决定长度的数组、运行期扩容容器或根据接收数据临时增长的实例集合；也不得用动态内存分配规避固定容量约束。
- 数组元素必须是对应的实例结构体，或由该层拥有且能完整表达单个实例状态的槽位结构体。每个元素的状态、缓存、计数器和回调上下文必须相互独立；只有明确设计的总线句柄和只读常量可以共享。
- 初始化和数据分发必须检查索引、设备地址或 ID 的范围与唯一性。处理循环的上限使用同一个数量宏，不得另写一个可能与实际硬件数量失配的常量。

```c
/* 该值来自当前项目的实际硬件配置，不在运行时改变。 */
#define MOTOR_NUM 4U

static Motor motorList[MOTOR_NUM];

void Motor_ProcessAll(void)
{
    for (uint32_t i = 0U; i < MOTOR_NUM; ++i) {
        Motor_Process(&motorList[i]);
    }
}
```

## 8. 初始化必须可重复调用且只执行一次

- 通信增强层和可独立组合的硬件驱动应提供幂等初始化入口，允许多个上层模块重复调用。
- 首次成功调用完成资源创建和 HAL 装配；后续调用不得重复创建任务、链表、队列、互斥量或重复注册回调。
- 多任务可能同时初始化时，必须保护初始化状态转换，但不得在长时间初始化过程中持续占用全局临界区。

## 9. 保持 CubeMX 再生成兼容性

- 不修改 STM32 HAL 官方库源码。
- 对 CubeMX 生成文件的集成修改应放在用户代码区，或放入独立的 FOS、驱动和应用模块中。
- 交付前检查 CubeMX 再次生成代码后，串口1日志入口、FreeRTOS 任务装配和各层初始化入口仍可保留或按文档恢复。

## 生成与检查要求

开始工程资源规划时，先应用本文件，再读取对应层的专用规范。至少检查：

- 串口1是否启用；未启用时是否记录原因和替代日志通道；
- RTOS 运行路径中是否存在 `HAL_Delay()`、忙等待或持锁延时；
- `osDelay()` 是否只出现在任务上下文，时间单位是否正确；
- 是否引入了不必要的任务、中断、消息或发送优先级；确需差异化优先级时是否记录充分依据和影响；
- ISR/HAL 回调是否只执行中断安全的短操作；
- 同一处理代码服务多个硬件实例时，是否使用由实际硬件数量宏决定的固定结构体数组，且没有使用 VLA、运行期扩容或动态分配；
- HAL、层级依赖、资源所有权和幂等初始化是否符合约束；
- CubeMX 再生成是否会覆盖必要集成代码。
