# 应用层书写规范

## 目的和边界

应用层建立在通信增强层和硬件驱动层已经提供的非阻塞接口、实时数据与事件回调之上，主要根据用户的实际项目需求完成硬件组合、轨迹规划、复合操作指令、工作状态机和安全策略。应用层约束应保持精简，优先表达项目本身的功能，不重复实现下层已经封装的通信协议、硬件控制和数据解析。

应用层负责：

- 将传感器、执行器及下级应用对象组合成具有独立意义的功能单元；
- 根据机构参数完成单位换算、运动学计算、轨迹规划和多器件协同；
- 将“抓取、迈步、回零、停止”等复合操作转换为一组可持续推进的状态和下层控制请求；
- 汇总下级对象的实时数据、状态和事件，向更高层提供稳定接口；
- 根据项目需求处理超时、故障、降级、重试、停止和锁止策略。

应用层不得直接访问外设寄存器或绕过驱动调用 HAL，也不得复制通信增强层或硬件驱动层已经实现的收发、协议解析和器件状态维护逻辑。

## 上位规则

生成或修改应用层代码前，应读取并遵守：

- `references/project-rules.md`：全工程共同遵守的头文件、执行上下文、延时、HAL 和资源所有权规则；
- `references/architecture-contract.md`：应用层与通信增强层、硬件驱动层、RTOS 及平台层的职责边界；
- `references/drivers.md`：硬件对象的公开数据、控制函数、回调和 `fatherArgs` 使用方式；
- `references/comms.md`：应用层收发外部命令和遥测数据时使用的公共通信接口；
- `references/standard.md`：工程现有的命名、结构体和源文件组织约定。

## 分层组合与代码复用

应用层应优先按可独立理解、可独立复用和可独立测试的功能单元划分，而不是把整台机器人全部写进一个文件。相同结构和行为应由同一类型的多个实例复用，不得为左右对称部件复制两套只有名称不同的实现。

例如，一个机器人具有两条腿和两只手臂时，可以先分别实现可复用的 `Leg` 和 `Arm` 应用对象，再由更高一级的 `Robot` 对象进行组合：

```text
Robot
├── Leg leftLeg
├── Leg rightLeg
├── Arm leftArm
└── Arm rightArm
```

两条腿应是同一个 `Leg` 类型的两个实例，共用状态机、轨迹规划和控制代码，同时各自保存独立的硬件绑定、实时数据和私有状态。左右方向、安装偏置、限位和机构参数应通过实例配置表达，不得通过复制源文件或散落的左右分支实现。

上级对象只通过下级对象的公开数据、控制函数和事件回调完成组合。上级可以把自己的地址写入下级对象的 `fatherArgs`，以便下级事件回调定位所属父对象；下级不得包含父对象类型，也不得自行决定其他同级对象的动作。

## 应用对象与封装

每个可独立使用的应用功能单元应由一个公开对象结构体表示。应用对象沿用硬件对象的公开与私有分离方式，通常包含：

1. **ReadOnly 实时数据和状态**：由本层根据下级数据计算并更新，使用者只读；物理量必须注明单位、有效范围和方向约定。
2. **ReadWrite 配置**：只放允许使用者直接调整、且不会绕过校验立即触发动作的参数。
3. **Private 私有数据入口**：公开结构体只保存不透明私有结构体指针 `priVari`，具体成员定义放在 `.c` 文件中。
4. **父级对象入口**：`fatherArgs` 由更高层装配，用于事件发生时定位所属父对象，不表示内存所有权。
5. **事件回调区**：至少可按需求提供实时数据刷新回调和功能事件回调。

```c
typedef struct _Leg_Private Leg_Private;
typedef struct _Leg Leg;

typedef enum {
    LEG_STATE_UNINITIALIZED = 0,
    LEG_STATE_IDLE,
    LEG_STATE_MOVING,
    LEG_STATE_STOPPING,
    LEG_STATE_ERROR
} Leg_State;

typedef void (*Leg_CallBack)(Leg *leg, void *fatherArgs);

struct _Leg {
    /* ReadOnly：由 Leg 内部更新，使用者只读。 */
    float nowLength; /* 单位：mm */
    float nowVelo;   /* 单位：mm/s */
    Leg_State state;
    uint32_t errorCode;

    Leg_Private *priVari;
    void *fatherArgs;

    /* 一组新的公开实时数据发布后触发一次。 */
    Leg_CallBack refreshDataCallBack;

    /* 按实际功能提供动作完成、到位、故障等事件。 */
    Leg_CallBack actionFinishedCallBack;
    Leg_CallBack errorCallBack;
};

bool Leg_Init(Leg *leg, const Leg_Config *config);
bool Leg_MoveTo(Leg *leg, float length, float velocity);
void Leg_Stop(Leg *leg);
void Leg_Process(Leg *leg);
```

具体对象只保留项目真实需要的数据、控制函数和事件，不为凑齐模板制造无意义字段。头文件应让使用者只阅读公开声明即可正确创建、装配和调用该对象，无需访问 `.c` 文件中的私有状态。

## 实时数据与事件回调

每个应用对象仍应根据需要向上提供两类接口：

- **实时刷新数据**：本对象汇总或计算得到的公开状态，例如腿长、末端位置、规划速度、当前动作和错误状态；
- **事件回调函数**：在一组实时数据发布、动作完成、状态到达或错误发生后通知上级对象。

实时数据应先在局部变量或私有暂存区中计算完成，再发布到公开区域。全部相关字段发布完成后，调用一次 `refreshDataCallBack(object, object->fatherArgs)`；没有新数据时不得伪造刷新事件。若多个字段必须属于同一个控制周期，应按照工程并发规则使用快照、序列计数器、双缓冲或临界区保证一致性。

回调的第一个参数固定为发生事件的当前应用对象，第二个参数固定传入该对象的 `fatherArgs`。回调为空时安全跳过。回调应优先提交状态请求或事件，不在 ISR、通信接收回调或软件定时器中执行耗时的轨迹计算、阻塞等待或连续操作多个硬件。

## 复合指令与状态机

复合操作指令应写成非阻塞的状态请求。公开函数负责参数校验、保存目标并请求进入相应状态；`Xxx_Process()` 在每个周期内只推进一步，不在一次调用中等待整个动作完成。

一个复合动作可以依次经历准备、启动、持续运行、受控停止、完成或错误等阶段。轨迹规划可以由应用对象在周期函数中增量计算，也可以提前生成有限轨迹后逐点下发；无论采用哪种方式，都应限制单周期计算量，并明确轨迹缓存的所有权和生命周期。

动作完成时，应先更新公开数据和状态，再对本次动作触发一次完成回调。进入新动作时清除完成事件锁存。持续跟踪或连续运行模式没有自然终点，不得每周期触发完成回调，只能由停止、模式切换、超时或故障退出。

## 周期处理与 RTOS

应用层不建议使用阻塞式程序。优先利用驱动层的非阻塞控制函数、数据刷新回调和事件回调推进状态机，禁止使用 `HAL_Delay()`、忙等待或依赖任务优先级形成隐含控制时序。

当应用对象需要固定控制周期、较多轨迹计算、事件串行化或独立执行上下文时，可以根据项目需求为其设置专门的 RTOS 主循环任务。任务及其名称、优先级和栈大小优先通过 CubeMX 的 FreeRTOS 配置创建；应用模块提供 `Xxx_Process()`，由 CubeMX 生成的任务入口或其用户代码区完成对象初始化并周期调用。任务应采用 `osDelayUntil()` 等稳定周期机制或通过事件、队列、任务通知唤醒。任务周期、优先级、栈大小、允许阻塞的 API、超时和最坏执行时间必须明确，且不得在循环中无条件忙转。

只有项目明确需要运行时动态创建和销毁任务时，才由应用代码调用 RTOS 创建接口；不得在应用初始化函数与 CubeMX 装配代码中重复创建同一个任务。对 CubeMX 生成文件的修改必须位于用户代码区，或者把具体逻辑放在独立的应用层源文件中，确保 CubeMX 再次生成代码后任务入口和调用关系仍然保留。

简单对象不必为了形式统一而单独创建任务，可以由更高层统一周期任务依次调用。是否建立专用任务取决于实时性、计算量、数据依赖和故障隔离需求，不取决于对象在组合树中的层级。

## 数据流与控制接口

应用层通过驱动公开接口读取传感数据、设置执行器目标和绑定事件，不得访问驱动的 `priVari`、源文件静态变量或底层 HAL 句柄。应用对象之间也遵循相同边界，只通过公开接口交互。

依赖减速比、丝杆导程、连杆尺寸、安装方向和零点偏置的单位换算属于应用层或专门的机构抽象层。转换后的物理量和控制量必须注明单位、方向、范围、饱和策略和无效值。

跨任务传递命令和状态时，应使用工程统一的队列、消息、临界区或快照机制。接口必须说明输入指针、轨迹数组和配置对象的所有权及有效期，不能依赖调用者的临时局部变量长期存在。

## 初始化与系统装配

应用对象的初始化通常负责：

- 校验配置和所有必需的下级对象；
- 绑定传感器、执行器或下级应用对象；
- 设置下级对象的 `fatherArgs` 和所需事件回调；
- 创建或绑定本实例的私有状态；
- 设置安全初始状态、清除事件锁存并初始化超时计时；
- 绑定由 CubeMX 配置的任务、队列、定时器等 RTOS 资源；仅在项目明确采用动态创建方案时由应用代码创建。

装配顺序应保证父对象及其回调上下文先有效，再启用可能产生事件的下级对象。父对象的生命周期必须覆盖所有下级对象可能调用回调的时间。解绑或销毁前，应先停止任务和事件源，再清空回调与 `fatherArgs`。

初始化应具有明确的重复调用行为，不得重复创建任务、队列、定时器或重复绑定同一资源。初始化失败时应返回可诊断错误，并保持对象处于不可运行或安全状态。

## 错误处理与安全状态

驱动负责报告硬件状态和错误，应用层负责结合机器人行为决定降级、停止、重试或锁止。每个应用对象应明确下级数据超时、命令超时、轨迹越界、硬件故障和通信中断时的处理策略。

错误处理仍应通过状态机分步完成。紧急停止可以调用驱动提供的立即安全接口；普通停止、回退、复位和多器件协调不得在一个回调中连续阻塞执行。错误回调按一次错误沿触发，错误未清除时不得每周期重复调用。

## 生成与检查

生成或修改应用层代码时，至少检查：

- 功能是否按可复用单元分层，同类左右部件是否使用同一类型的不同实例；
- 上级是否只通过下级的公开数据、控制函数、回调和 `fatherArgs` 完成组合；
- 是否避免直接访问 HAL、外设寄存器、驱动私有数据或重复实现下层协议；
- 公开对象是否提供必要的实时数据、刷新回调和功能事件，并隐藏私有状态；
- 复合指令是否只提交请求，周期函数是否每次只推进一步并快速返回；
- 轨迹规划的周期、计算量、边界、缓存所有权和完成条件是否明确；
- 是否避免 `HAL_Delay()`、忙等待和依赖优先级的隐含时序；
- 专用 RTOS 任务是否确有需要，并明确周期、优先级、栈、唤醒方式、超时和最坏执行时间；
- RTOS 任务是否优先通过 CubeMX 创建，应用初始化是否避免重复创建，CubeMX 再生成后任务入口是否仍能保留；
- 多任务或回调之间的数据共享是否采用正确的同步或快照机制；
- 初始化是否完成下级绑定、回调注册和安全状态设置，重复调用和失败路径是否安全；
- 下级故障、数据超时和通信异常是否能够进入明确的降级、停止或锁止状态；
- 公开数据和控制量是否注明单位、方向、范围、有效性及饱和策略。
