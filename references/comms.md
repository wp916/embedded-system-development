# 通信增强层生成规范

## 目的和边界

通信增强层位于 STM32 HAL 与硬件驱动层之间。它在不改变 ST 官方 HAL 底层驱动行为的前提下，为 UART、CAN、SPI、I2C 等通信方式补充适合 FreeRTOS 多任务系统的发送排队、连续传输、接收注册和数据分发机制。

通信增强层只处理通信资源和数据传输，不解释机器人业务命令，不执行应用状态机，也不包含特定器件的控制策略。

## 公共代码库与复用原则

通信增强层不应针对每个机器人工程重复设计。相同 STM32 HAL 接口下，同一种通信方式的 FOS 增强代码应接近完全复用；工程差异应尽量收敛到启用宏、HAL 句柄映射、缓冲容量和接收注册容量等配置项。

`assets/firmware-template/comms/` 是本 Skill 持续维护的通信增强层公共代码库，其中 `UART/` 和 `CAN/` 提供对应通信增强层的实现示例。后续生成新的通信增强层时，应参考这两个示例的模块结构、HAL 封装方式、发送缓冲机制、完成回调、接收注册、数据分发和初始化方式，再结合目标通信方式的 HAL 接口及通信模型进行适配。

为目标工程集成某种通信方式 `Xxx` 时，必须按以下顺序处理：

1. 先在 `assets/firmware-template/comms/<Xxx>/` 中查找 `Fos_Xxx.h/.c`、`DList_Xxx.h/.c` 及其配置说明。
2. 公共代码库已有完整且符合本规范的实现时，直接复制并集成，不为当前工程重新生成另一套核心实现；只修改宏变量、全局变量这类工程侧配置。若旧示例仍在阻塞式发送中调用 `PushHead_DList`，应先在公共代码库中完成本规范要求的兼容升级，再进行复用。
3. 公共代码库尚无该通信方式时，以库内 UART 和 CAN 示例的模块结构、发送链表、完成回调、接收注册和幂等初始化机制为参考，结合目标 HAL 的真实通信模型生成新实现。
4. 新实现完成检查后，既集成到当前目标工程，也保存到 `assets/firmware-template/comms/<Xxx>/`，供后续工程直接复用。不得只把唯一实现留在某个具体项目中。
5. 已有模块不能满足新工程需求时，在公共代码库中进行升级并按 `a.b` 规则更新版本号，再让当前工程和后续工程使用升级后的统一公共版本；不要为新工程创建不受维护的项目专用分支。

向后兼容升级应尽量保持已有公共函数名、参数、返回语义、回调格式、配置宏含义和正常发送顺序。确需改变接口时，应提供兼容包装或迁移说明，并用旧工程调用方式和新需求同时验证。

### 公共代码库版本规则

通信增强层公共代码库的版本号至少使用两级整数格式 `a.b`：

- `a` 是主版本号。`a` 相同的所有版本必须保证已有同名接口的使用效果完全兼容；不仅要能够通过编译，还必须保持函数参数与返回值含义、阻塞或异步语义、超时单位、排队顺序、缓冲区所有权、回调触发条件以及正常错误处理方式兼容。
- `b` 是功能更新号。在不破坏上述兼容性的前提下，新增功能、新增接口、缺陷修复、性能优化或内部实现调整时递增 `b`。
- 删除或重命名已有接口、改变已有函数签名，或者改变同名接口的使用效果且无法通过兼容包装保持旧行为时，必须递增 `a`，并将 `b` 重新从 `0` 开始。
- 如果新实现可以通过保留旧接口或提供兼容包装，使旧工程不修改调用代码即可保持原使用效果，则允许保持 `a` 不变并递增 `b`。
- 每种通信方式的公共模块独立维护版本号。版本至少应在公开头文件中以主、次版本宏声明，例如 `FOS_UART_VERSION_MAJOR` 和 `FOS_UART_VERSION_MINOR`；工程集成记录中使用 `a.b` 形式记录实际采用的版本。

升级公共代码库前，必须先判断改动属于兼容功能更新还是不兼容更新，并据此确定版本号。不得在改动同名接口使用效果后仍沿用原主版本号。

无论首次生成还是后续升级，都必须保持通信层边界：通信增强层只处理通信资源和数据传输，不解释机器人业务命令，不执行应用状态机，也不包含特定器件的控制策略。器件协议识别和业务动作应留在注册的硬件驱动接收函数或更高层中。

## 核心设计

### 保持 HAL 底层不变

- 不修改 `Drivers/STM32*_HAL_Driver/` 中的官方源文件。
- 默认只使用 HAL 公共 API，只有用户明确要求且 HAL 确实不能满足已经声明的需求时，才另行评估 LL 实现。
- 尽可能不要直接操作外设寄存器，以避免硬件替换时的bug，如果直接操作外设寄存器，要在明显处标注潜在硬件不兼容。
- 继续使用目标通信方式已有的 HAL 句柄、发送函数、接收函数和完成回调。
- 自定义代码通过 HAL 公开 API、动态回调注册接口或 CubeMX 用户代码区完成集成。
- 如果目标 HAL 不支持动态注册回调，应在 CubeMX 生成的弱回调或用户代码区转发到 FOS 层，不得直接修改官方库实现。

### 统一命名和文件结构

为通信方式 `Xxx` 生成：

```text
Fos_Xxx.h
Fos_Xxx.c
DList_Xxx.h
DList_Xxx.c
```

公开增强接口使用 `FOS_Xxx_` 前缀，内部类型和函数使用统一的 `Xxx` 标识。已有工程的大小写风格不一致时，应遵循目标工程现有命名，但同一模块内必须保持一致。

### HAL 发送函数的镜像封装

对需要增强的 HAL 发送函数生成同构的 FOS 包装函数：

```c
HAL_Xxx_Transmit(...)      -> FOS_Xxx_Transmit(...)
HAL_Xxx_Transmit_IT(...)   -> FOS_Xxx_Transmit_IT(...)
HAL_Xxx_Transmit_DMA(...)  -> FOS_Xxx_Transmit_DMA(...)
```

包装函数应尽量保持原 HAL 函数的句柄、数据、长度和返回类型，使硬件驱动层能够直接从 `HAL_` 调用迁移到对应的 `FOS_` 调用。

STM32 在本框架中通过 FreeRTOS 调度多个任务，形成单核硬件上的伪并行运行。不得使用忙循环、`HAL_Delay()` 或任何持续占用 CPU 的方式等待通信资源。

`FOS_Xxx_Transmit(..., Timeout)` 这类带超时参数的阻塞式接口，直接在调用它的任务中等待通信资源，不再把请求插入链表头部，也不为此创建独立的通信定时扫描任务。资源暂时不可用时调用 `osDelay(1)`，使当前调用任务进入阻塞态并让出 CPU；其他控制、采样、通信和安全任务仍可正常调度。

基本逻辑如下：

```c
uint32_t start_tick = osKernelGetTickCount();

for (;;) {
    HAL_StatusTypeDef status = FOS_Xxx_TryClaimAndStart(handle, data, size);

    if (status == HAL_OK) {
        return HAL_OK;
    }
    if (status != HAL_BUSY) {
        return status;
    }
    if (FOS_Xxx_TimeoutExpired(start_tick, timeout_ticks)) {
        return HAL_TIMEOUT;
    }

    osDelay(1);
}
```

`FOS_Xxx_TryClaimAndStart()` 表示原子地检查并占用通信资源，然后启动底层 HAL 发送。检查与占用必须由短临界区或互斥机制保护，避免多个任务同时观察到空闲；调用 `osDelay()` 前必须退出临界区并释放互斥量。不得从 ISR 或 HAL 中断回调调用这种阻塞式接口。

`osDelay(1)` 表示一个 RTOS tick，不应默认等同于 1 ms。若公开接口的 `Timeout` 单位为毫秒，应根据内核 tick 频率换算为 `timeout_ticks`，或者使用系统 tick 计算实际经过时间。该机制实现的是单任务阻塞：等待期间只有调用 `FOS_Xxx_Transmit()` 的任务暂停，处理器可以运行其他任务。启动成功、超时和不可重试的 HAL 错误必须通过返回值明确区分。

## 发送缓冲机制

### 每个通信实例独立管理

每个启用的通信实例应定义一个 FOS 通信句柄。该句柄强制包含原始 HAL 通信句柄和发送缓冲链表：

```c
typedef struct {
    HAL_Xxx_HandleTypeDef *hal_handle;
    DList_Xxx tx_queue;
    /* 其他私有对象根据目标通信方式和代码逻辑设置 */
} FOS_Xxx_Handle;
```

除原始 HAL 通信句柄和发送链表外，不强制所有通信方式使用相同的私有成员。`id`、忙碌标志、发送状态、临时缓冲、锁、统计量和错误状态等对象，应根据目标 HAL 的工作方式、发送推进逻辑和诊断需求决定。

不同外设实例不得共享同一个发送链表。存在多个通信实例时，应根据代码结构建立原始 HAL 句柄与 FOS 通信句柄之间的可靠对应关系；可以使用查找函数，也可以使用静态绑定或其他清晰方式。收到未知或未注册的原始句柄时必须返回明确错误，不得解引用空指针。

### 链表节点和数据所有权

新的通信增强层应直接复用 `assets/firmware-template/comms/UART/DList_Uart.h` 和 `DList_Uart.c` 的程序结构，通常不需要修改链表的核心逻辑。复制并改名为 `DList_Xxx.h/.c` 后，应保留：

- `DNode` 的前驱、后继、数据指针和数据长度；
- `DList` 的头结点、尾结点、`loadingFirstFlag` 和实际长度；
- `CopyData`、`DeleteData`、`Create`、`PushTail`、`PopHead` 和 `PopTail` 的对应功能；
- 节点数据申请、数据复制、节点弹出和内存释放的原有顺序；
- 插入和弹出链表时对共享指针及长度的临界区保护；
- 首个节点尚未写入完成时，由 `loadingFirstFlag` 防止发送完成回调读取半成品数据的机制。

必要修改应限制在通信名称、类型名称、包含文件、内存接口，以及节点实际存储的数据格式。CAN 可在节点数据中包含 ID、DLC 和帧类型，SPI/I2C 可包含片选、从机地址、方向或事务阶段，但不应因此重新设计链表算法。

除非现有实现已被证明无法满足需求或存在明确缺陷，不要把双向链表替换成 FreeRTOS 队列、环形缓冲区、固定块内存池或其他容器，也不要重写已经验证的插入、弹出和并发保护流程。确需修改时，应保持原接口兼容并记录修改原因。

对于直接启动 `HAL_Xxx_Transmit_DMA()` 的数据，FOS 层不需要为了延长数据生命周期而增加额外复制、托管或保护逻辑。应在 `Fos_Xxx.h` 的 DMA 发送接口上给出明确注释，要求调用者保证发送数据在本次 DMA 发送完成前始终存在且不得被修改，例如：

```c
/**
 * @notice 调用者必须保证 pData 指向的数据从函数调用开始，
 *         直到对应 DMA 发送完成回调触发前始终有效且内容不被修改。
 */
HAL_StatusTypeDef FOS_Xxx_Transmit_DMA(
    HAL_Xxx_HandleTypeDef *handle,
    const uint8_t *pData,
    uint16_t size);
```

这属于使用 HAL DMA 接口时调用者应遵守的基本约定，不在源文件中为错误的数据生命周期使用方式增加特殊兼容。通信资源忙碌时，等待发送的数据仍按照本层的链表缓冲逻辑保存，并由链表实现负责其排队期间的数据有效性。

### 排队和连续发送

排队与连续发送也应直接沿用 `Fos_Uart.c` 的程序结构，通常只替换 HAL 句柄类型、HAL 异步发送函数、发送完成回调以及链表节点的数据格式。其核心流程保持不变：

1. 阻塞式 `FOS_Xxx_Transmit(..., Timeout)` 在通信资源空闲时原子地占用资源并启动 HAL 发送；资源忙碌时按照前文的 `osDelay(1)` 逻辑等待，直至启动成功或超时，不进入发送链表。
2. 异步 `FOS_Xxx_Transmit_IT/DMA` 在通信资源忙碌时，调用 `PushTail_DList` 将数据复制到链表尾部，然后立即返回。
3. HAL 发送完成回调检查链表；链表中存在待发送数据时，调用 `PopHead_DList` 取出首项，并立即启动下一次 HAL 异步发送。
4. 链表为空时，按该模块的状态管理方式恢复通信资源为空闲状态。
5. 链表只承担异步接口的 FIFO 排队，不使用头插法改变已经排定的数据顺序。

发送路径统一使用 `PushTail_DList` 保持 FIFO，不得调用 `PushHead_DList`。尤其不得用头插法实现阻塞式发送、超时等待、优先发送或修复发送完成竞态；有优先级需求时，应另外设计明确且可验证的队列策略。

链表连接关系、通信模块实际采用的发送状态，以及“空闲转发送中”的判断仍按照 `DList_Uart` 和 `Fos_Uart` 已验证的临界区边界处理。是否需要独立的 `busy` 标志属于通信句柄的私有实现，不改变上述链表排队流程。

### 发送完成与恢复

发送完成回调负责推进队列，不要求调用发送者等待。回调必须：

- 确认回调对应正确的 HAL 句柄；
- 完成当前帧的生命周期处理；
- 安全取得下一帧；
- 调用 HAL 异步发送函数启动下一帧；
- 队列为空时把实例恢复为空闲状态；
- 记录 HAL 启动失败，并进入可诊断的恢复路径。

HAL 发送完成回调通常运行在中断上下文，不能调用 `osDelay()`，也不能调用带 `Timeout` 的阻塞式 FOS 接口。阻塞式 `FOS_Xxx_Transmit()` 已在调用任务中等待资源并且不写入链表头部，因此回调不需要使用 `UART_SoftTimerCallBack`、延时等待或 `PushHead_DList` 处理这类竞态；回调只按正常流程完成当前发送、弹出异步队列的队首并启动下一帧。

## 接收注册与分发

### 标准接收处理函数

每种通信方式必须定义统一的接收结果和函数指针类型。具体参数可以随通信方式调整，但必须包含接收数据、长度、必要的帧元数据和注册者上下文：

```c
typedef enum {
    FOS_XXX_RX_NOT_MINE = 0,
    FOS_XXX_RX_HANDLED  = 1,
    FOS_XXX_RX_ERROR    = 2
} FOS_Xxx_RxResult;

typedef FOS_Xxx_RxResult (*FOS_Xxx_RxHandler)(
    HAL_Xxx_HandleTypeDef *hal_handle,
    const FOS_Xxx_RxFrame *frame,
    void *device);
```

`FOS_Xxx_RxFrame` 应封装该通信方式识别一帧所需的信息。例如 UART 包含数据指针和长度，CAN 还包含 ID、DLC 和帧类型，I2C/SPI 应包含主从角色、地址或事务信息。

### 接收函数绑定

提供公开注册函数，把设备实例和接收处理函数绑定到指定通信实例：

```c
FOS_Xxx_Status FOS_Xxx_RegisterReceiver(
    HAL_Xxx_HandleTypeDef *hal_handle,
    void *device,
    FOS_Xxx_RxHandler handler);
```

注册表必须属于具体通信实例，至少保存 `device` 和 `handler`。注册时检查：

- HAL 句柄是否受支持；
- 处理函数是否为空；
- 注册表是否已满；
- 同一设备和处理函数是否重复注册；
- 注册发生在初始化前还是初始化后，以及两种顺序是否均被支持。

注册容量应由配置项决定。注册失败必须通过返回值报告，不能只打印日志。

### 顺序询问规则

HAL 接收事件到达后，FOS 层构造标准接收帧，并按照注册顺序调用处理函数：

1. 返回 `FOS_XXX_RX_NOT_MINE`：继续询问下一个注册者。
2. 返回 `FOS_XXX_RX_HANDLED`：认为数据已经被认领并处理，立即停止分发。
3. 返回 `FOS_XXX_RX_ERROR`：记录解析错误；是否继续分发由该通信模块明确规定，默认停止。
4. 所有注册者均返回 `NOT_MINE`：增加未识别帧计数，并按配置选择丢弃、交给默认处理器或输出诊断。

必须记录接收处理函数的调用上下文。若分发直接发生在 HAL/ISR 回调中，处理函数只能完成快速校验、数据复制、状态更新或任务通知；协议解析、日志格式化、阻塞操作和复杂控制应转移到任务上下文。

完成分发后，应按该通信方式要求及时重新启动下一次 HAL 接收。重新接收失败必须记录并进入恢复路径。

## 一次性初始化

每种通信增强层必须提供一个公开初始化函数，例如：

```c
FOS_Xxx_Status FOS_InitXxx(void);
```

该函数允许被应用层、多个硬件驱动或系统装配代码重复调用，但整个通信增强层只初始化一次。首次成功调用应完成：

- 初始化每个启用实例的 FOS 句柄和发送链表；
- 注册发送完成、接收完成和错误回调；
- 初始化接收缓冲区并启动异步接收；
- 创建必要的发送恢复任务、通知对象或诊断资源；
- 清零统计状态并将模块标记为就绪。

后续调用不得重复创建链表哨兵、任务、队列或回调资源，应直接返回第一次初始化的结果。初始化状态至少区分 `UNINITIALIZED`、`INITIALIZING`、`READY` 和 `FAILED`，避免多个任务同时首次调用导致重复创建。状态检查和切换必须受临界区或等效一次性机制保护，但耗时的 HAL 初始化过程不能一直占用临界区。

如果允许初始化失败后重试，必须先完整回滚已创建资源；否则固定返回第一次失败结果。不得在状态不明时部分重复初始化。

注册机制与初始化机制应相互兼容：不同驱动可以各自在自身初始化函数中先调用 `FOS_InitXxx()`，再注册自己的接收处理函数，而不需要知道其他驱动的初始化顺序。

## 生成步骤

为一种新的通信方式生成增强层时：

1. 搜索 `assets/firmware-template/comms/`，确认目标通信方式是否已有可复用实现及其 `a.b` 版本；没有时读取库内 UART 和 CAN 实现示例。
2. 阅读目标 STM32 HAL 头文件和用户工程的 CubeMX 配置，列出句柄类型、异步发送入口、完成回调、接收入口、错误回调和硬件限制。
3. 已有实现满足需求且符合本规范时直接复用；只生成目标工程需要的配置、句柄映射和集成入口。发现阻塞式发送仍使用 `PushHead_DList` 时，按本规范先升级公共实现。
4. 已有实现缺少能力时，先判断版本兼容性：能够保持所有同名接口使用效果兼容时递增 `b`；不能保持时递增 `a` 并把 `b` 归零。随后升级公共实现，并验证旧用法与新需求。
5. 没有实现时，判断通信模型是字节流、消息帧还是主从事务，再以 `Fos_Uart` 和 `DList_Uart` 为结构母版生成 `Fos_Xxx.h/.c` 与 `DList_Xxx.h/.c`，不能直接套用 UART 帧模型。
6. 将首次生成或升级后的通用模块保存到 `assets/firmware-template/comms/<Xxx>/`，同时集成到目标工程的 `Core/Inc`、`Core/Src` 和 Keil 工程组。
7. 输出 CubeMX 配置要求，包括 DMA、NVIC、回调注册、接收模式、IRQ 优先级和 FreeRTOS 可调用优先级限制；只在 CubeMX 用户区添加初始化或转发代码。
8. 完成静态检查和测试，记录复用来源、公共库 `a.b` 版本、主次版本变更依据、兼容性验证、主动修正的缺陷以及通信方式特有的差异。

## 必须验证的行为

- 初始化函数从不同驱动重复调用时，资源只创建一次。
- 空闲发送可以立即启动；资源忙碌时，阻塞式发送只阻塞调用任务并在超时后返回 `HAL_TIMEOUT`，异步发送按 FIFO 顺序进入链表。
- 阻塞式发送不调用 `PushHead_DList`，也不进入发送链表；异步发送路径只使用 `PushTail_DList`。
- 多任务同时调用同一实例时，通信资源的检查与占用是原子的，不会重复启动发送、破坏链表或丢失发送状态。
- 不同通信实例的队列和回调互不干扰。
- 连续多个发送完成回调可以自动清空队列，无需发送者轮询。
- 直接 DMA 发送的数据遵守头文件声明的调用者生命周期约定；链表中的排队数据在轮到发送并完成前始终有效，完成、失败和终止路径没有内存泄漏。
- 注册者能按顺序收到数据，首个返回 `HANDLED` 的处理函数终止后续询问。
- 注册表满、未知句柄、空处理函数、未识别帧和 HAL 错误都有明确返回值或统计信息。
- 接收重启失败和发送启动失败不会让模块永久保持错误的忙碌状态。
- CubeMX 再次生成代码后，通信增强层及其集成入口仍然保留。
- 公共模块头文件声明有效的 `a.b` 版本；同一主版本下，旧工程对已有同名接口的调用无需修改，并保持原有使用效果。

## 不得机械继承的实现细节

`Fos_Uart` 是首要参考实现，但以下内容必须根据目标工程重新确定：

- `USE_UARTx`、收发缓冲长度和设备注册数量；
- UART 定长/不定长接收模式及 IDLE 中断逻辑；
- `DList_Uart` 所依赖的 `mymalloc`、`myfree` 和内存区域标识；目标工程没有相同内存接口时只做接口适配，保持节点申请、数据复制和释放逻辑不变；
- 高优先级插队、USMART、`printf` 重定向和调试告警；
- 不同 STM32 系列的 DMA、IRQ、HAL 回调注册能力；
- CAN、SPI、I2C 等通信方式的帧元数据和事务状态机；
- 参考工程中为规避特定现象设置的首次空帧过滤、轮询恢复或自定义 IRQ 实现。

这些项目只有在用户需求、目标 HAL 行为或硬件测试能够证明需要时才加入新模块。
